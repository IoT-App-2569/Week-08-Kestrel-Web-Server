# ใบงานการทดลองที่ 8.1 (Labsheet 8.1)
#### [Checkpoint 1.1 ทดสอบความเข้าใจ]

1. ในหน้าจอ Terminal ขณะที่เซิร์ฟเวอร์กำลังรันอยู่ ให้กดปุ่ม `Ctrl + C` เพื่อหยุดโปรแกรม
2. กลับไปที่หน้าเบราว์เซอร์แล้วกดปุ่ม **Refresh (F5)** สังเกตว่าเกิดอะไรขึ้น และอธิบายสั้นๆ ว่าทำไมจึงเป็นเช่นนั้น
   - **คำตอบ** เบราว์เซอร์จะเปิดหน้าเว็บไม่ได้
  

## คำถามท้ายการทดลอง (Review Questions)
1. ในสถาปัตยกรรมของ Kestrel ตัวแปร `builder` ทำหน้าที่อะไร และตัวแปร `app` ทำหน้าที่อะไร
```text
- builder (WebApplicationBuilder) ใช้ "เตรียมและตั้งค่า" ก่อนเริ่มเซิร์ฟเวอร์ เช่น โหลดค่า Configuration (appsettings.json,
Environment) ตั้งค่า Logging ลงทะเบียน Services (Dependency Injection) และตั้งค่า Kestrel เช่นพอร์ต
- app (WebApplication) คือแอปที่สร้างเสร็จแล้วจาก builder.Build() ใช้กำหนด Middleware และเส้นทาง (Route) เช่น
app.MapGet(...) ว่า URL ไหนให้ตอบอะไร และเมื่อเรียก app.Run() จะเริ่ม Kestrel ให้รอรับ Request
```
2. เปรียบเทียบความสะดวกระหว่างการสร้าง Web Server บน .NET Minimal API กับการรันผ่าน LAMP Stack (Apache + PHP) ว่ามีข้อดีข้อเสียต่างกันอย่างไรในมุมมองของงาน IoT Gateway
```text
- .NET Minimal API
  ข้อดี: เป็นโปรแกรมเดียวจบ มีเว็บเซิร์ฟเวอร์ในตัว ไม่ต้องติดตั้ง/คอนฟิกหลายโปรแกรม รันได้ทั้ง Windows/Linux/Raspberry Pi
  ทำงานเร็ว (คอมไพล์แล้ว รองรับ async) แปลง Object เป็น JSON ให้อัตโนมัติ และรันงานเบื้องหลังได้ในโปรเซสเดียวกัน
  เช่น อ่าน Serial หรือรอฟัง MQTT จาก ESP32 ตลอดเวลา
  ข้อเสีย: ต้องติดตั้ง .NET Runtime หรือ build แบบ self-contained ซึ่งไฟล์ใหญ่หลายสิบ MB ต้องคอมไพล์ใหม่ทุกครั้งที่แก้โค้ด
  และโฮสต์ราคาถูกทั่วไปรองรับน้อยกว่า PHP

- LAMP Stack (Apache + PHP)
  ข้อดี: แพร่หลาย มีตัวอย่างและโฮสต์ราคาถูกเยอะ แก้ไฟล์ .php แล้วใช้ได้ทันทีไม่ต้องคอมไพล์
  ข้อเสีย: ต้องติดตั้งและตั้งค่าหลายส่วน (Apache, PHP, MySQL) PHP ทำงานแบบ "1 Request = 1 รอบสคริปต์แล้วจบ"
  จึงไม่เหมาะกับงานที่ต้องรันค้างตลอด เช่น รอรับข้อมูลเซนเซอร์ต่อเนื่อง และต้องแปลง JSON เอง (json_encode, header)

```
3. นักศึกษาคิดว่าการเพิ่ม `/api/` เข้าไปใน route นั้นมีประโยชน์อย่างไรบ้าง ถ้าไม่ใส่จะเกิดปัญหาอะไรบ้าง
```text
- ประโยชน์
  1. แยกชัดเจนว่า /api/... เป็นข้อมูล JSON สำหรับเครื่อง (ESP32, แอปมือถือ) ส่วน path อื่นเป็นหน้าเว็บสำหรับคน
  2. กันชื่อชนกัน เช่น /status อาจเป็นหน้าเว็บแสดงสถานะ ขณะที่ /api/status ส่ง JSON ให้อุปกรณ์
  3. ตั้งค่ากับ API ทั้งกลุ่มได้ในครั้งเดียว เช่น ยืนยันตัวตน, CORS, จำกัดจำนวน Request (ใน .NET ใช้ app.MapGroup("/api"))
  4. ทำเวอร์ชันได้ง่าย เช่น /api/v1/led กับ /api/v2/led ให้อุปกรณ์รุ่นเก่ายังใช้ได้
  5. ตั้ง Reverse Proxy หรือ Firewall ให้ส่งต่อเฉพาะ /api/ ไปยังเซิร์ฟเวอร์ได้ง่าย

- ถ้าไม่ใส่
  เส้นทางข้อมูลกับหน้าเว็บ/ไฟล์ static ปนกันและอาจชนกัน ใส่กฎความปลอดภัยเฉพาะส่วน API ได้ยาก
  ผู้ใช้หรืออุปกรณ์แยกไม่ออกว่า URL ไหนคืนข้อมูล และเมื่อระบบใหญ่ขึ้นจะดูแลและเพิ่มเวอร์ชันได้ยาก
```

# ใบงานการทดลองที่ 8.2
#### [Checkpoint 2.1 ทดสอบความเข้าใจ]
1. ใน ESP-IDF v6.x ฟังก์ชัน `adc_oneshot_read()` คืนค่าผลลัพธ์เป็นตัวเลขแบบใด และมีช่วงค่าต่ำสุด-สูงสุดเท่าใดเมื่อตั้งค่าเป็น `ADC_BITWIDTH_12`
   - **คำตอบ:** คืนค่าเป็นตัวเลขจำนวนเต็ม (Integer / int) โดยมีช่วงค่าตั้งแต่ 0 ถึง 4095 (เนื่องจากความละเอียดแบบ 12-bit หรือ $2^{12} = 4096$ ระดับ) ซึ่งสอดคล้องกับช่วงแรงดันไฟฟ้า 0 ถึง 3.3 โวลต์ที่รับเข้ามา
1. ทำไมเราจึงต้องกดปุ่ม `Ctrl + ]` เพื่อปิด **ESP-IDF Monitor** ก่อนที่เราจะรันโปรแกรมฝั่ง C# Kestrel ในใบงานถัดไป
   *(คำใบ้: หากโปรเซส idf.py monitor ยังเปิดค้างอยู่ จะเกิดอะไรขึ้นกับพอร์ต COM)*
   - **คำตอบ:** เพราะโปรเซส idf.py monitor จะทำการ ครอบครองและล็อกพอร์ต COM (COM Port Locking) ของบอร์ด ESP32 ไว้ใช้งานแต่เพียงผู้เดียว หากไม่ปิดหน้าต่าง Monitor เสียก่อน โปรแกรมฝั่ง C# (Kestrel) จะไม่สามารถเปิดพอร์ต COM เพื่ออ่านข้อมูลสตรีมเซนเซอร์ได้ ทำให้เกิดข้อผิดพลาดในการเชื่อมต่อ (Port Access Denied / Serial Port Busy)

# ใบงานการทดลองที่ 8.3
#### 📋 [Checkpoint 3.1: ทดสอบกลไก Fallback Simulation]
1. ขณะที่โปรแกรม C# กำลังรันอยู่ ให้ถอดสาย USB ของ ESP32 ออกจากคอมพิวเตอร์
2. กด Refresh (F5) บนหน้าเบราว์เซอร์หลายๆ ครั้งติดต่อกัน สังเกตว่า:
   - ค่า `dataSource` เปลี่ยนเป็นอะไร?
   - ค่า `rawValue` ยังเปลี่ยนได้อยู่หรือไม่ และเปลี่ยนในลักษณะใด?
   - **คำตอบ:** ค่า `dataSource` ค่าจะเปลี่ยนเป็น "Simulation Mode (Sine Wave)" อัตโนมัติ ค่า `rawValue` ยังคงเปลี่ยนแปลงได้ โดยจะเปลี่ยนไปตามฟังก์ชันคลื่นไซน์ (Sine Wave) เป็นจังหวะต่อเนื่องราบรื่นระหว่างช่วง 0 ถึง 4095 โดยอัตโนมัติ
